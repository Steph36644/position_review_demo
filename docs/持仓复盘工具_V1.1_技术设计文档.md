## 二、技术栈选型

### 2.1 选型总表

| 层次 | 选型 | 理由 |
|---|---|---|
| 前端框架 | 原生 JavaScript（ES6+） | 延续 v0.0 技术栈，零迁移成本；单页单用户无需框架开销 |
| UI 样式 | Tailwind CSS（CDN） | 延续 v0.0，已验证可用 |
| 图表 | Chart.js 4.x（CDN） | 延续 v0.0 饼图/条形图 |
| OCR | Tesseract.js 5.x（浏览器端，chi_sim+eng） | v0.0 已集成本地 OCR，隐私好、零后端、已验证；云端 API 作为可选开关 |
| 结构化数据存储 | localStorage（JSON 序列化） | 延续 v0.0，适合 KV 结构的小数据 |
| 大对象存储（截图） | IndexedDB | 突破 localStorage 5MB 限制；单张截图可达数 MB，localStorage 会超限 |
| 构建/部署 | 无构建，纯静态文件 | `file://` 直接打开，无需服务器 |
| ID 生成 | 时间戳 + 4 位随机串 | 本地单设备，无需 UUID 复杂度；可排序、可调试 |

### 2.2 关键选型决策说明

#### 决策 1：OCR 方案 — Tesseract.js（本地）+ 云端 API（可选，默认关闭）

**PRD 待决项 1**。v0.0 已集成 Tesseract.js 并完成灰度预处理 + 放大 + 90s 超时，实测可用。v1.1 继续以 Tesseract.js 为主路径，满足"截图不外传"的隐私铁律。云端 OCR（如百度/腾讯 OCR）作为可选开关：

- 默认关闭，UI 上提供"启用云端 OCR（准确率更高，截图将上传至第三方）"复选框；
- 启用前必须弹二次确认告知数据外传；
- 云端失败时自动回退到 Tesseract.js，不阻塞流程。

#### 决策 2：截图存储介质 — IndexedDB

**PRD 待决项 2**。localStorage 容量约 5MB，单张截图 base64 即可占满，多张必然超限。v1.1 将 `DB.snapshots[date].image_base64` 迁移至 IndexedDB，localStorage 仅保留快照元数据（date / ocr_status / confirmed / image_id）。`image_id` 为 IndexedDB 中的 key。

#### 决策 3：配比策略 — 用户手选（v1.1 默认），预留 FIFO 开关

**PRD 待决项 3**。v1.1 按 PRD §3.2.4 实现用户手选 `linked_buy_ids` + `linked_qty_map`。`linked_qty_map` 结构为 `{buyTradeId: consumedQty}`。代码层预留 `matchingStrategy` 常量，v1.2 可切换为 `fifo`。

#### 决策 4：trade.id — 时间戳 + 随机后缀

**PRD 待决项 4**。格式 `t{yyMMddHHmmss}{4位随机}`，如 `t260930153012a3f7`。优点：本地可读、可按时间排序、冲突概率极低（单用户）。若未来做多设备同步，可平滑切换为 UUID，因 `id` 仅作内部关联键，外部无依赖。

#### 决策 5：OCR 置信度阈值 — 0.7

**PRD 待决项 5**。Tesseract.js 每个 word 带 `confidence`（0-100）。低于 70 的字段在预填表格中标红，提示用户手填；全部字段 confidence ≥ 70 时 ocr_status=success，否则 partial。

#### 决策 6：数据迁移 — 增量兼容，原地升级

**PRD 待决项 6**。v0.0 的 `DB.holdings` / `DB.overview` / `uploadedSnapshots` / `review_{date}` / `plan_*` 数据结构不变，v1.1 直接读取。新增 `DB.trades`、`DB.reviews`、`DB.snapshots`（元数据），首次运行时初始化为空。`uploadedSnapshots` 中的截图在 v1.1 迁移到 IndexedDB（见第十一章）。

#### 决策 7：性能预算 — 内存索引 + 按需计算

**PRD 待决项 7**。trades 全部加载到内存（单用户数据量小，500 条约 < 500KB），构建以下内存索引加速查询：
- `indexByDate`: Map<date, Trade[]>
- `indexByName`: Map<name, Trade[]>
- `indexById`: Map<id, Trade>
- `openBuysByName`: Map<name, Trade[]>（qty_open > 0 的 buy/add）

索引在每次写操作后增量更新，R3 对账查询 O(n) 内完成。

## 三、总体架构设计

### 3.1 分层架构

```
┌──────────────────────────────────────────────────────────────┐
│  View 层（HTML + 渲染函数）                                    │
│  持仓看板 / 交易流水 Tab / 理由对账 Tab / 复盘 Tab / 弹窗      │
└──────────────────────────┬───────────────────────────────────┘
                           │ 事件绑定 + 数据绑定
┌──────────────────────────▼───────────────────────────────────┐
│  Controller 层（表单校验 + 交互编排）                          │
│  TradeFormController / ReconciliationController /             │
│  ReviewController / SnapshotController                        │
└──────────────────────────┬───────────────────────────────────┘
                           │ 调用业务接口
┌──────────────────────────▼───────────────────────────────────┐
│  Service 层（业务逻辑）                                        │
│  TradeService  │ MatchingEngine(DAA-1) │ ReviewService │      │
│  SnapshotService(OCR) │ HoldingsService                       │
└──────────────────────────┬───────────────────────────────────┘
                           │ 读写数据
┌──────────────────────────▼───────────────────────────────────┐
│  Repository 层（存储抽象）                                     │
│  LocalStorageRepo（trades/reviews/holdings/overview/snapshots-meta）│
│  IndexedDBRepo（snapshots.image_base64）                      │
└──────────────────────────────────────────────────────────────┘
```

**分层规则**：
- View 不直接操作 localStorage/IndexedDB，必须经 Controller → Service → Repository。
- Service 之间可调用（如 MatchingEngine 被 TradeService 和 ReconciliationController 共享）。
- Repository 不感知业务，仅做 CRUD 与序列化。

### 3.2 模块划分与依赖

```
                            │  fillTodaySnapshot│

┌─────────────────┐
```

**依赖方向**：View → Controller → Service → Repository。Service 之间：MatchingEngine 被多个 Service 共享；无循环依赖。

### 3.3 目录与文件结构

v0.0 为单 HTML 文件（65KB）。v1.1 功能显著增加，拆分为模块化文件以便维护，仍保持纯静态、无构建：

```
v1.1/

├── css/
│   └── style.css               # 玻璃拟态、状态色、弹窗样式（从 v0.0 内联抽出）
├── js/
│   ├── constants.js            # 枚举（action/sell_type/reason_type/expected_period/ocr_status）
│   ├── utils.js                # fmt/colorClass/storageKey/id 生成 等工具
│   ├── models.js               # TypeScript 风格 JSDoc 类型定义 + 默认值工厂
│   ├── repositories/
│   │   ├── localStorageRepo.js # trades/reviews/holdings/overview/snapshots-meta
│   │   └── indexedDBRepo.js    # snapshots.image_base64
│   ├── services/
│   │   ├── tradeService.js     # R1/R2 createTrade/getOpenBuys/deleteTrade
│   │   ├── matchingEngine.js   # DAA-1 calcQtyOpen/getReconciliationView
│   │   ├── reviewService.js    # S1 fillTodaySnapshot/saveReview
│   │   ├── snapshotService.js  # DAQ-6 upload/ocr/confirm
│   │   └── holdingsService.js  # DAQ-2 holdings/overview 读写
│   ├── controllers/
│   │   ├── tradeFormController.js  # R1/R2 弹窗表单校验
│   │   ├── reconciliationController.js # R3 筛选/渲染

│   │   └── snapshotController.js   # DAQ-6 上传/预填/确认
│   └── app.js                  # 初始化：DB 加载、Tab 切换、renderAll
```

**加载顺序**（index.html 中 `<script>` 顺序）：
`constants.js → utils.js → models.js → repositories → services → controllers → app.js`

### 3.4 代码规范

- 延续 v0.0 风格：`var`/`function` 与 ES6+ 混用，本设计统一使用 ES6+（`const`/`let`/箭头函数/模板字符串/解构）。
- 模块以 IIFE 暴露到全局命名空间 `App`（如 `App.TradeService.createTrade`），避免全局污染。
- 所有 Service 函数必须有 JSDoc 注释，标明参数类型与返回值。
- 数值计算统一用 `Number`，金额保留 2 位小数、价格保留 4 位（PRD §3.1.2），百分比保留 2 位。
- 不使用 `eval`、不动态生成函数。

## 四、数据模型设计

### 4.1 存储介质分配

| 数据集合 | 存储介质 | Key 格式 | 容量预估 |
|---|---|---|---|
| DB.overview[date] | localStorage | `pr_overview` | 每日 1 条，1 年 < 50KB |
| DB.holdings[date] | localStorage | `pr_holdings` | 每日 5-15 条，1 年 < 1MB |
| DB.trades[] | localStorage | `pr_trades` | 每笔约 400B，500 笔 < 200KB |
| DB.reviews[date] | localStorage | `pr_reviews` | 每日 1 条，1 年 < 200KB |
| DB.snapshots[date]（元数据） | localStorage | `pr_snapshots` | 每日 1 条（不含图），1 年 < 20KB |
| DB.snapshots[date].image_base64 | IndexedDB | `snap_{date}` | 每图 1-5MB，按需清理 |
| 持仓卡片计划文本（v0.0 遗留） | localStorage | `plan_{date}_{name}_{type}` | 兼容 v0.0 |

> localStorage key 统一加 `pr_` 前缀，与 v0.0 的 `review_{date}` / `uploadedSnapshots` 做隔离；v0.0 旧 key 由迁移脚本一次性读取后写入新 key。

### 4.2 核心实体与字段

#### 4.2.1 Trade（交易流水）— 对应 PRD §4.1

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| id | string | 是 | `t{yyMMddHHmmss}{rand4}`，唯一 | 主键 |
| date | string | 是 | `YYYY-MM-DD` | 交易日期 |
| name | string | 是 | 非空 | 标的名称（v1.3 关联 instruments） |
| action | enum | 是 | `buy`/`add`/`sell`/`reduce`/`clear` | 方向 |
| amount | number | 是 | 正整数 | 数量 |
| price | number | 是 | > 0，4 位小数 | 成交价 |
| buy_reason | string | buy/add 必填 | 1-100 字 | 核心理由 |
| reason_type | enum | buy/add 必填 | 基本面/技术面/事件/估值/情绪 | 理由类型 |
| expected_period | enum | buy/add 必填 | 短期(<1月)/中期(1-3月)/中期(3-6月)/长期(>6月) | 预期持有周期 |
| invalid_condition | string | buy/add 必填 | 1-100 字 | 失效条件 |
| target_price_low | number | buy/add 必填 | > 0 | 目标区间下沿 |
| target_price_high | number | buy/add 必填 | ≥ target_price_low | 目标区间上沿 |
| stop_loss | number | buy/add 必填 | > 0 | 止损位 |
| sell_type | enum | sell/reduce/clear 必填 | 兑现/证伪/失效/违规 | 卖出四分类 |
| sell_note | string | sell/reduce/clear 必填；违规时 ≥5 字 | - | 卖出说明 |
| linked_buy_ids | string[] | sell_type ∈ {兑现,证伪,失效} 必填；违规为空 | - | 关联买入 id |
| linked_qty_map | object | sell_type ∈ {兑现,证伪,失效} 必填 | `{buyId: qty}`，qty 正整数 | 各买入消耗数量 |
| created_at | string | 系统 | ISO 时间戳 | 创建时间 |
| updated_at | string | 系统 | ISO 时间戳 | 更新时间 |

**字段互斥规则**：
- `action ∈ {buy, add}` → 买入字段必填，卖出字段为 `null`/`[]`/`{}`。
- `action ∈ {sell, reduce, clear}` → 卖出字段必填，买入字段为 `null`。

**索引**（内存索引，见 2.2 决策 7）：
- `indexById`：按 id 查单条。
- `indexByName`：按标的查所有交易（R2/R3 用）。
- `indexByDate`：按日期查（S1 用）。
- `openBuysByName`：按标的查未平仓买入（R2 用，qty_open > 0）。

#### 4.2.2 Review（每日复盘）— 对应 PRD §4.1

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| operations | object[] | 是 | 当日操作列表，元素 `{name, action, reason_type, amount, price}` |
| pnl_attribution | object | 是 | `{name: 归因标签}`，v1.1 用户手填，v1.2 S2 联动填充 |
| position_in_band | boolean \| null | 是 | v1.1 恒为 null（预留），v1.2 P1-2 计算写入 |
| tomorrow_plan | string | 是 | 明日计划 |
| created_at | string | 系统 | ISO 时间戳 |
| updated_at | string | 系统 | ISO 时间戳 |

Key：`date`（`YYYY-MM-DD`）。

#### 4.2.3 Snapshot（截图附件元数据）— 对应 PRD §4.1

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| image_id | string | 是 | IndexedDB 中的 key，格式 `snap_{date}` |
| uploaded_at | string | 是 | ISO 时间戳 |
| ocr_status | enum | 是 | success/partial/failed/skipped |
| ocr_raw | object \| null | 否 | OCR 原始结果（仅 success/partial 留存） |
| confirmed | boolean | 是 | 是否已确认落库 holdings/overview |
| confirmed_at | string \| null | 否 | 确认时间 |

Key：`date`。`image_base64` 本体存于 IndexedDB，key = `image_id`。

#### 4.2.4 Overview / Holdings（沿用 v0.0，不变）

- `DB.overview[date] = {date, total_assets, market_value, floating_pnl, day_pnl, day_pnl_pct, available, withdrawable, position_pct}`
- `DB.holdings[date] = [{date, name, market_value, position, available, cost, current_price, day_pnl, day_pnl_pct, floating_pnl, floating_pnl_pct, cleared}]`

### 4.3 ER 关系

```
Trade (buy/add) 1 ──── N linked_buy_ids ──── N Trade (sell/reduce/clear)
     │                                                   │
     │ name                                              │ name
     ▼                                                   ▼
  Holdings[date].name（弱关联，v1.3 起通过 instruments 强关联）

Review[date].operations[].name ──弱关联──▶ Trade.name / Holdings.name

Snapshot[date] ──1:1──▶ Holdings[date]（confirmed=true 时）
Snapshot[date] ──1:1──▶ Overview[date]
```

- Trade 自关联：卖出通过 `linked_buy_ids` 关联买入，`linked_qty_map` 记录消耗数量。
- Holdings/Review/Snapshot 均以 `date` 为分区键，与 Trade 通过 `name` 弱关联。

### 4.4 数据完整性约束

| 约束 | 实现位置 | 说明 |
|---|---|---|
| 买入 7 字段必填 | TradeFormController + TradeService | 保存按钮禁用 + 服务端二次校验 |
| 卖出 sell_type 必填 | 同上 | - |
| 违规 sell_note ≥ 5 字 | 同上 | - |
| linked_buy_ids 非空（非违规） | TradeService | 服务端校验，防绕过前端 |
| Σ linked_qty_map ≤ Σ 选中买入 qty_open | TradeService | 超出抛 `LinkedBuyNotEnoughException` |
| target_price_low ≤ target_price_high | TradeFormController | 不满足时保存按钮禁用 |
| stop_loss / target / price 数值合法 | TradeFormController | - |
| name 非空 | TradeFormController | - |
| 重复 date+name+action+amount+price | 不约束 | 允许同日多笔 |

### 4.5 数据存储策略

- **写入策略**：所有写操作先更新内存 `DB` 对象与索引，再同步序列化到 localStorage；IndexedDB 异步写入截图。
- **读取策略**：页面加载时从 localStorage 一次性加载全部结构化数据到内存；截图按需从 IndexedDB 读取（仅在查看截图时）。
- **备份策略**：提供"导出全部数据"按钮（JSON 下载）与"导入数据"按钮，防止 localStorage 被清除。
- **清理策略**：snapshots 超过 30 天的 image_base64 可由用户手动清理（元数据保留）。

## 五、核心模块设计

### 5.1 R1 买入理由结构化记录（TradeService.createTrade）

#### 5.1.1 业务流程

```
用户提交 R1 表单
    │
```

#### 5.2.2 未平仓数量计算（DAA-1 核心）

```javascript
// matchingEngine.js
const MatchingEngine = (function() {
  // 计算单笔买入的未平仓数量
  function calcQtyOpen(buyTradeId) {
    const buy = IndexManager.getById(buyTradeId);
    if (!buy || !['buy', 'add'].includes(buy.action)) return 0;
    let consumed = 0;
    // 遍历所有卖出，累加 linked_qty_map[buyTradeId]
    IndexManager.getAllSells().forEach(sell => {
      if (sell.linked_qty_map && sell.linked_qty_map[buyTradeId]) {
        consumed += sell.linked_qty_map[buyTradeId];
      }
    });
    return Math.max(0, buy.amount - consumed);
  }

  // 获取某标的未平仓买入列表
  function getOpenBuys(name) {
    return IndexManager.getByName(name)
      .filter(t => ['buy', 'add'].includes(t.action))
      .map(t => ({ ...t, qty_open: calcQtyOpen(t.id) }))
      .filter(t => t.qty_open > 0);
  }
})();
```

**复杂度优化**：`calcQtyOpen` 若每次全量遍历 sells，R3 在 500 笔时可能超 500ms。优化方案：
- 维护 `consumedQtyById` 内存缓存（Map<buyId, consumedQty>），每次卖出写入时增量更新；
- 删除/修改卖出时重算受影响的买入。

#### 5.5.2 OCR 解析关键算法

沿用 v0.0 的 `parseSnapshotText` 思路，核心步骤：
1. OCR 文本按行分割；
2. 遍历已知标的名，找到含该名的行作为该标的的起始行；
3. 从该行提取后续数字，按列顺序映射到 position / available / cost / current_price / floating_pnl；
4. 每个提取值标注 confidence（取 Tesseract word confidence）。

**异常变动检测**：与 `DB.holdings[最近日期]` 对比，若某标的 position 变化 > 50%，标红提示"数量大幅变化，请确认"。

## 七、状态机设计

### 7.1 交易生命周期状态机（对应 PRD §4.3）

```
                ┌─────────────┐
买入记录创建    │   OPEN      │  qty_open = amount
─────────────▶ │  （未平仓）  │
                └──────┬──────┘
                       │ 卖出关联（兑现/证伪/失效）
                       ▼
                ┌─────────────┐
                │  PARTIAL    │  0 < qty_consumed < amount
                │  （部分平仓）│
                └──────┬──────┘
                       │ 累计消耗 = amount
                       ▼
                ┌─────────────┐
                │   CLOSED    │  qty_open = 0
                │  （已平仓）  │
                └─────────────┘
```

**违规卖出**：不改变任何买入记录状态，独立标记为 `VIOLATION`。

### 7.2 状态判定规则

| 状态 | 判定条件 | 视觉 |
|---|---|---|
| OPEN | consumed = 0 | 灰色空圆 |
| PARTIAL | 0 < consumed < amount | 黄色半圆 |
| CLOSED | consumed ≥ amount 且至少一条关联卖出 | 绿色对勾 |
| VIOLATION | 该买入存在 sell_type=违规 的关联卖出 | 深红警告（叠加于上述状态） |

**状态计算时机**：
- 每次 `createTrade`（卖出）后，增量更新受影响买入的 consumed；
- `deleteTrade` / `updateTrade` 后，重算受影响买入；
- R3 渲染时从 `consumedQtyById` 缓存读取，无需重算。

### 7.3 Snapshot OCR 状态机

```
uploaded ──OCR success──▶ success ──confirm──▶ confirmed
     │                       │
     ├─OCR partial─────▶ partial ──confirm──▶ confirmed
     │                       │
     └─OCR failed──────▶ failed ──回退手动──▶ skipped
                                                  │
```

## 八、关键技术点与难点

### 8.1 难点 1：买卖配对与未平仓数量计算（DAA-1）

**问题**：一笔买入可能被多笔卖出部分消耗，需准确计算每条买入的 qty_open，且 R3 对账需高效查询。

**方案**：
- 数据结构：`linked_qty_map: {buyId: consumedQty}` 存在卖出记录上，支持多对多配比。
- 缓存：`consumedQtyById: Map<buyId, number>` 内存缓存，写操作时增量更新。
- 增量更新算法：
  ```
  创建卖出 sell：
    for (buyId, qty) of sell.linked_qty_map:
      consumedQtyById[buyId] += qty
  删除卖出 sell：
    for (buyId, qty) of sell.linked_qty_map:
      consumedQtyById[buyId] -= qty
  qty_open(buyId) = buy.amount - consumedQtyById[buyId]
  ```
- 启动时全量重建缓存（遍历 trades 一次，O(n)）。

**风险**：若 `linked_qty_map` 数据损坏（如 qty 为负），qty_open 可能为负。**应对**：`calcQtyOpen` 中 `Math.max(0, ...)` 兜底；`validateSell` 中校验 qty 为正整数。

### 8.2 难点 2：R1/R2 表单校验的"保存按钮层强制"

**问题**：PRD 铁律"任一必填字段为空，保存按钮禁用"，需防止用户绕过。

**方案**：
- 双重校验：Controller 层实时校验控制按钮 disabled 状态；Service 层 `createTrade` 二次校验抛异常。
- 实时校验：表单 `input` 事件触发 `validateForm()`，返回 `{valid, errors}`，按钮 `disabled = !valid`。
- 错误提示：字段红框 + 红字提示，按钮 disabled 时 hover 提示具体缺失字段。

### 8.3 难点 3：截图 OCR 准确率与隐私平衡

**问题**：Tesseract.js 本地 OCR 准确率一般，云端 OCR 涉及隐私。

**方案**：
- 默认 Tesseract.js + 图像预处理（灰度、放大、对比度增强），v0.0 已验证。
- 云端 OCR 作为可选开关，启用前二次确认，失败自动回退。
- OCR 结果仅预填，用户逐项确认后才落库，低置信度标红。
- 截图存 IndexedDB，不外传（除非用户主动启用云端 OCR）。

### 8.4 难点 4：localStorage 容量管理

**问题**：localStorage 约 5MB，截图 base64 会超限。

**方案**：
- 截图本体迁移 IndexedDB，localStorage 仅存元数据。
- 提供"数据导出/导入"与"清理 30 天前截图"功能。
- 写入时捕获 `QuotaExceededError`，提示用户清理。

### 8.5 难点 5：v0.0 数据平滑迁移

**问题**：v0.0 的 `uploadedSnapshots`（含 base64）存 localStorage，可能已占满容量；`review_{date}` 为纯文本，v1.1 需升级为结构化 4 段。

**方案**：见第十一章数据迁移方案。

## 十、数据迁移方案

### 10.1 迁移范围

v0.0 → v1.1 的数据迁移：

| v0.0 数据 | 新位置 | 迁移动作 |
|---|---|---|
| `DB` 内置（holdings/overview/dates） | `DB.holdings` / `DB.overview` | 不变，直接使用 |
| `localStorage.uploadedSnapshots[date]`（含 holdings/overview） | `DB.holdings[date]` / `DB.overview[date]` + IndexedDB 截图 | holdings/overview 已在 v0.0 合并到 DB，截图迁移到 IndexedDB |
| `localStorage.review_{date}`（纯文本） | `DB.reviews[date]` | 纯文本放入 `tomorrow_plan` 或新增 `legacy_text` 字段（v1.1 仅做展示，不强制结构化） |
| `localStorage.plan_{date}_{name}_{type}` | 保留 | v0.0 持仓卡片计划文本，v1.1 仍支持读取（非核心） |
| 无 | `DB.trades` | 初始化为空 |
| 无 | `DB.snapshots` | 初始化为空 |

### 10.2 迁移脚本

```javascript
// migration.js，在 app.js 初始化时执行一次（版本号标记）
function migrateV0ToV1() {
  const version = localStorage.getItem('pr_version');
  if (version === 'v1.1') return; // 已迁移

  // 1. 迁移 uploadedSnapshots 的截图到 IndexedDB
  const ups = JSON.parse(localStorage.getItem('uploadedSnapshots') || '{}');
  Object.keys(ups).forEach(date => {
    if (ups[date].image_base64) {
      IndexedDBRepo.saveImage('snap_' + date, ups[date].image_base64);
      DB.snapshots[date] = {
        image_id: 'snap_' + date,
        uploaded_at: ups[date].uploaded_at || new Date().toISOString(),
        ocr_status: 'success',
        confirmed: true,
        confirmed_at: ups[date].uploaded_at || new Date().toISOString()
      };
    }
  });

  // 2. 迁移 review_{date} 纯文本到 DB.reviews
  Object.keys(localStorage).forEach(key => {
    if (key.startsWith('review_')) {
      const date = key.replace('review_', '');
      const text = localStorage.getItem(key) || '';
      if (!DB.reviews[date]) {
        DB.reviews[date] = {
          operations: [],
          pnl_attribution: {},
          position_in_band: null,
          tomorrow_plan: text,
          created_at: new Date().toISOString(),
          updated_at: new Date().toISOString()
        };
      }
    }
  });

  // 3. 持久化新结构
  StorageRepo.saveReviews();
  StorageRepo.saveSnapshots();
  localStorage.setItem('pr_version', 'v1.1');
}
```

### 10.3 回滚策略

迁移前将 v0.0 数据导出为 JSON 备份（`localStorage.pr_backup_v0`），若迁移失败可手动恢复。迁移标记 `pr_version` 控制只执行一次。

## 十一、性能与容量设计

### 11.1 性能预算

| 操作 | 目标响应时间 | 数据规模 |
|---|---|---|
| R3 对账页渲染 | < 500ms | trades ≤ 500 |
| R2 弹窗加载未平仓买入 | < 100ms | 单标的 ≤ 50 笔 |
| S1 一键填入快照 | < 100ms | 当日 trades ≤ 20 |
| 页面首次加载 | < 1s | 全部数据 < 2MB |
| OCR 识别 | < 30s | 单张截图 |

### 11.2 性能优化措施

1. **内存索引**：`indexById` / `indexByName` / `indexByDate` / `openBuysByName` / `consumedQtyById`，避免全量遍历。
2. **防抖**：复盘自动保存 500ms 防抖，避免频繁写入 localStorage。
3. **按需渲染**：R3 对账页按标的分组后仅渲染当前可视区域（trades > 200 时启用虚拟滚动，v1.1 可选）。
4. **IndexedDB 异步**：截图读写异步，不阻塞主线程。
5. **localStorage 批量写**：一次操作只序列化一次，而非每个字段单独写。

### 11.3 容量预估

| 数据项 | 单条大小 | 1 年预估 | 5 年预估 |
|---|---|---|---|
| trades | ~400B | 500 条 = 200KB | 1MB |
| reviews | ~500B | 250 条 = 125KB | 625KB |
| holdings | ~300B/条 × 10 | 250 天 = 750KB | 3.75MB |
| overview | ~200B | 250 条 = 50KB | 250KB |
| snapshots 元数据 | ~300B | 250 条 = 75KB | 375KB |
| **localStorage 合计** | - | **~1.2MB** | **~6MB** |
| snapshots 图片（IndexedDB） | 2-5MB/张 | 250 张 = 500MB-1.25GB | 2.5-6GB |

> localStorage 5 年可能接近 6MB，超出 5MB 限制。**应对**：v1.1 末期或 v1.2 将 holdings/overview 也迁移 IndexedDB，或提供"归档历史数据"功能。v1.1 阶段（1 年）1.2MB 安全。

- 实际未维护该索引，改为：`consumedQtyById: Map<buyId, consumedQty>` 增量缓存 + `getOpenBuys(name)` 时对 `indexByName` 动态过滤 `amount - consumed > 0`。
- 原因：`openBuysByName` 需在每次消耗变化时同步维护，与消耗数据双写存在不一致风险；单用户数据量下动态过滤成本可忽略，且单一数据源更可靠。
- 增量更新落地：卖出写入/摘除时由 IndexManager `applyConsumption(linked_qty_map, ±1)` 维护缓存；编辑场景另以 `recalcConsumedFor` 全量重算兜底（对应 8.1 的增量算法）。
