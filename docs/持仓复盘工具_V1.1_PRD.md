> **范围声明**：本文件仅覆盖 v1.0 PRD 中归属于 v1.1 的功能（R1/R2/R3/S1 + DAQ-1/2/6 + DAA-1），不改变 v1.0 已确定的产品定位、痛点分析、不做边界与版本路线。任何与 v1.0 冲突的描述以 v1.0 为准。

## 二、核心用户故事

> 用"用户故事"形式串联 v1.1 的全部功能，确保功能设计始终围绕"我是否真的会每天用"。

### US-1：新建一笔买入并填写理由
**作为**我自己，**当**新建一笔买入或加仓时，**我希望**系统强制我填齐 7 个理由字段，
**以便**这笔买入的理由在未来卖出时可作为对照依据，事后也能复盘验证。

**验收路径**：交易录入流 → R1 弹窗 → 必填校验 → 写入 trades → 对账页可见

### US-2：卖出一笔持仓并强制对照
**作为**我自己，**当**卖出或减仓时，**我希望**系统自动列出该标的的未平仓买入记录，
**以便**我必须选择"兑现/证伪/失效/违规"并关联到具体买入记录（违规则强制说明），
**确保**卖出动作不脱离买入理由。

**验收路径**：交易录入流 → R2 弹窗（自动带出未平仓买入）→ 四选一 + 关联 → 校验 → 写入 trades → DAA-1 配对 → R3 闭环状态更新

### US-3：用截图快速录入当日持仓快照
**作为**我自己，**当**盘后录入当日持仓时，**我希望**上传一张交易软件持仓页截图，
**以便**OCR 预填持仓量/成本/现价等字段，我逐项确认后即落库，节省录入时间。

**验收路径**：盘后复盘流 → DAQ-6 截图上传 → OCR 预填 → 逐项确认 → 落库 holdings/overview + 留存 snapshot

### US-4：查看历史买卖配对与违规
**作为**我自己，**当**不定期回看时，**我希望**按标的分组查看历史"买-卖"配对，
**以便**识别违规交易、判断体系执行质量。

**验收路径**：对账查看流 → R3 Tab → 按标的分组 → 违规清单红色高亮

### US-5：完成每日结构化复盘
**作为**我自己，**当**盘后 10–20 分钟复盘时，**我希望**4 段式模板可"一键填入今日快照"，
**以便**快速完成复盘并自动保存，而非从零写流水账。

**验收路径**：盘后复盘流 → S1 复盘区 → 一键填入 → 补主观判断与明日计划 → 自动保存 reviews

## 三、功能详细需求

### 3.1 R1 买入理由结构化记录

#### 3.1.1 功能描述
新建持仓或加仓时，强制录入以下结构化字段。无这些字段则交易记录无法保存。

#### 3.1.2 字段定义

| 字段 | 类型 | 是否必填 | 取值/约束 | 用途 |
|---|---|---|---|---|
| 标的名称（name） | string | 必填 | 沿用现有 Demo 命名；v1.3 起关联 instruments | 唯一标识 |
| 方向（action） | enum | 必填 | `buy` / `add` | 区分新建/加仓 |
| 数量（amount） | number | 必填 | 正整数 | 持仓量 |
| 价格（price） | number | 必填 | 正数，4 位小数 | 成交价 |
| 核心理由（buy_reason） | string | 必填 | 一句话，1–100 字 | 卖出对照依据 |
| 理由类型（reason_type） | enum | 必填 | 基本面 / 技术面 / 事件 / 估值 / 情绪 | v1.3 理由命中率分类 |
| 预期持有周期（expected_period） | enum | 必填 | 短期(<1月) / 中期(1–3月) / 中期(3–6月) / 长期(>6月) | v1.3 持仓时长分析 |
| 失效条件（invalid_condition） | string | 必填 | 1–100 字 | R2 选择"失效"时的对照依据 |
| 目标区间上沿（target_price_high） | number | 必填 | ≥ price | R2 选择"兑现"时的对照 |
| 目标区间下沿（target_price_low） | number | 必填 | ≤ target_price_high | 目标区间完整性 |
| 止损位（stop_loss） | number | 必填 | < price | R2 选择"证伪"时的对照 |
| 交易日期（date） | date | 必填 | 默认今日，可改 | 流水时序 |

#### 3.1.3 交互流程

```
[入口] 持仓卡片"加仓"按钮 / 顶部"记一笔交易"按钮
   ▼
R1 弹窗（含上述 12 字段表单）
   ├─ action 默认按入口判断（新建=buy，加仓=add）
   ├─ name 默认带入（加仓时）/ 手动输入（新建时）
   └─ 实时校验：
       ├─ 价格/数量/止损/目标区间数值合法性
       ├─ target_price_low ≤ target_price_high
       └─ stop_loss < price ≤ target_price_low（推荐约束，可放行为警告）
   ▼
[保存] 触发必填校验 → 任一必填字段为空 → 保存按钮禁用 + 红字提示
   ▼
校验通过 → 写入 DB.trades（含 linked_buy_id=null）→ 关闭弹窗 → 持仓卡片刷新
```

#### 3.1.4 边界条件
- **新建后立即部分卖出**：v1.1 不支持"同一笔买入跨日部分卖出"，部分卖出时按比例拆分 linked_buy_id（v1.2 可优化）。
- **目标区间下沿 > 现价**：允许保存，但弹窗提示"目标下沿已高于现价，请检查"。
- **止损位 ≥ 现价**：允许保存，但弹窗提示"止损位高于现价，可能立即触发"。

#### 3.1.5 v1.2/v1.3 扩展点
- v1.2 归因联动：S2 读取 `buy_reason` + `reason_type` 给当日盈亏打"体系内"默认标签。
- v1.3 标的主数据：`name` 字段关联 `DB.instruments[name]`，自动带入行业/风格。
- v1.3 理由命中率：基于 `reason_type` + `sell_type` 统计兑现/证伪/失效分布。

### 3.2 R2 卖出动作强制对照

#### 3.2.1 功能描述
卖出/减仓/清仓时，系统自动带出该标的的未平仓买入记录，强制用户选择四分类之一并关联具体买入（违规除外）。

#### 3.2.2 卖出四分类定义

| sell_type | 含义 | 必填字段 | 触发场景 |
|---|---|---|---|
| 兑现 | 买入理由兑现，达到目标区间 | linked_buy_id + sell_note（一句话） | 价格触及 target_price_high |
| 证伪 | 买入理由被证伪，触及止损 | linked_buy_id + sell_note | 价格跌破 stop_loss |
| 失效 | 买入理由失效（不再成立） | linked_buy_id + sell_note | invalid_condition 触发 |
| 违规 | 无对应买入理由的卖出 | sell_note（强制，≥5 字） | 情绪化/无计划卖出 |

#### 3.2.3 交互流程

```
[入口] 持仓卡片"减仓/清仓"按钮 / 顶部"记一笔交易" → 选 sell/reduce/clear
   ▼
R2 弹窗（左侧表单 + 右侧未平仓买入列表）
   ├─ 右侧自动查询 DB.trades 中 name=标的 且 未被完全关联合并的 buy/add 记录
   ├─ 用户填：数量、价格、日期
   ├─ 用户选 sell_type
   │   ├─ 兑现/证伪/失效 → 必须勾选 linked_buy_id（可多选，按数量配比）
   │   └─ 违规 → linked_buy_id 灰显，sell_note 必填且 ≥5 字
   └─ 实时校验：数量 ≤ 选中的买入记录未平仓数量之和
   ▼
[保存] 触发必填校验
   ▼
校验通过 → 写入 DB.trades（sell_type / linked_buy_id / sell_note）→ DAA-1 配对引擎更新 → R3 刷新
```

#### 3.2.4 未平仓数量配比逻辑（DAA-1 子逻辑）

```
对每条 buy/add 记录维护"未平仓数量"：
  qty_open(t) = qty(t) - Σ qty_consumed_by_sells_linked_to_t

卖出校验：
  若 sell_type ∈ {兑现, 证伪, 失效}：
    Σ 选中买入的 qty_open ≥ 本次卖出数量 → 通过
  若 sell_type = 违规：
    不消耗任何 qty_open，但本次违规数量会被 R3 红色高亮
```

#### 3.2.5 边界条件
- **未平仓买入记录不存在**：强制 sell_type 只能选"违规"，linked_buy_id 列表灰显。
- **减仓数量等于持仓**：自动转为 clear，行为同 sell。
- **跨多笔买入的部分卖出**：允许多选 linked_buy_id，按 FIFO 或用户手选顺序配比（v1.1 默认手选，v1.2 可加 FIFO/FIFO/LIFO 开关）。
- **同一笔买入被多次卖出**：累加消耗，qty_open 减至 0 后从可选列表移除。

#### 3.2.6 v1.2/v1.3 扩展点
- v1.2 归因联动：S2 自动将 sell_type=违规 的盈亏归为"体系外"。
- v1.3 理由命中率：基于 sell_type × reason_type 统计兑现率。
- v2.x 违规统计：基于 sell_type=违规 计数与占比。

### 3.3 R3 理由-交易对账视图

#### 3.3.1 功能描述
新增独立 Tab/页面，按标的分组展示买卖配对，违规交易独立红色高亮，支持筛选。

#### 3.3.2 视图结构

```
[筛选区] 日期范围 / 标的 / sell_type / 是否闭环
   ▼
[违规清单小节]（默认折叠，仅当存在违规时显示）
   ├─ 红色卡片列出所有 sell_type=违规 的交易
   └─ 显示：标的 / 日期 / 数量 / 价格 / sell_note / "无对应买入理由"
   ▼
[按标的分组配对列表]
   ├─ 标的 A
   │   ├─ 买入 #001（2026-09-10, 1000股, 理由摘要）— 已完全平仓
   │   │     └─ 卖出（2026-09-20, 兑现, 1000股）
   │   ├─ 买入 #002（2026-09-15, 500股, 理由摘要）— 部分平仓（300/500）
   │   │     └─ 卖出（2026-09-22, 证伪, 300股）
   │   └─ 买入 #003（2026-09-25, 800股, 理由摘要）— 未平仓
   ├─ 标的 B ...
   └─ ...
```

#### 3.3.3 配对状态定义

| 状态 | 含义 | 视觉 |
|---|---|---|
| 已完全平仓 | qty_open = 0 且至少一条关联卖出 | 绿色对勾 |
| 部分平仓 | 0 < 关联卖出数量 < qty | 黄色半圆 |
| 未平仓 | 无关联卖出 | 灰色空圆 |
| 闭环违规 | 存在 sell_type=违规 的关联卖出 | 深红警告 |

#### 3.3.4 筛选与排序
- 默认：按标的名称升序、买入日期升序
- 筛选器：日期范围 / 标的（多选）/ sell_type（多选）/ 闭环状态（多选）
- 排序：标的、买入日期、卖出日期、数量

#### 3.3.5 v1.2/v1.3 扩展点
- v2.x 违规统计：基于违规清单聚合月度/周度统计。
- v2.x 历史检索：在筛选区扩展关键词搜索（理由文本、说明文本）。

### 3.4 S1 结构化复盘模板（基础版）

#### 3.4.1 功能描述
替代 V1.0 Demo 的自由文本框，提供 4 段式折叠面板，支持"一键填入今日快照"，自动保存至 DB.reviews。

#### 3.4.2 4 段定义

| 段位 | 字段 | v1.1 数据来源 | v1.2 升级方向 |
|---|---|---|---|
| ① 今日操作 | operations[] | 从 DB.trades 当日流水聚合（标的+方向+理由类型） | 同 v1.1，可加违规高亮 |
| ② 盈亏归因 | pnl_attribution{标的:归因} | v1.1：用户手动填（默认空） | v1.2：S2 自动联动填充（理由未变→体系内；违规→体系外） |
| ③ 仓位水位是否越界 | position_in_band: bool | v1.1：字段预留但不计算（默认 null） | v1.2：P1-2 计算后写入 |
| ④ 明日计划 | tomorrow_plan: string | 用户手填 | 同 v1.1 |

#### 3.4.3 交互流程

```
[入口] 复盘区"展开模板"按钮
   ▼
4 段折叠面板展开
   ├─ "一键填入今日快照"按钮（位于段位栏右上角）
   │   ├─ ① operations = DAA-1 聚合当日 trades
   │   ├─ ② pnl_attribution = {} （v1.1 留空，等用户手填）
   │   ├─ ③ position_in_band = null （v1.1 留空，v1.2 由 P1-2 填充）
   │   └─ ④ tomorrow_plan = 上次复盘的明日计划（便于追踪）
   ▼
用户补充主观判断 → 自动保存 localStorage（输入即保存，防丢失）
   ▼
可选：导出当日复盘为文本（v1.1 可选，v1.3 PDF 导出在 C09 不属于范围）
```

#### 3.4.4 边界条件
- **当日无交易**：① 段为空数组，仍可保存。
- **当日未生成 holdings 快照**：② 段无盈亏数据，仅显示持仓列表占位。
- **历史复盘已存在**：再次展开直接加载历史值，不覆盖。

#### 3.4.5 v1.2/v1.3 扩展点
- v1.2：②③ 段从手动 → 联动自动填充。
- v1.3：① 段加入行业切片预览链接。

### 3.5 DAQ-6 持仓界面截图上传（OCR）

#### 3.5.1 功能描述
盘后录入持仓时，可上传一张交易软件持仓页截图，OCR 识别后预填字段，用户逐项确认后落库。

#### 3.5.2 数据流

```
[上传] 用户选择 PNG/JPG（≤5MB）
   ▼
[本地存储] base64 写入 DB.snapshots[date].image_base64
   ▼
[OCR 识别]（v1.1 候选方案二选一，技术方案阶段决定）
   ├─ 方案A：浏览器端 Tesseract.js 本地识别（隐私好，准确率一般）
   └─ 方案B：调用云端 OCR API（准确率高，但需用户授权数据外传）
   ▼
[预填表格] OCR 结果以可编辑表格形式呈现
   ├─ 列：标的 / 持仓量 / 可用 / 成本 / 现价 / 浮动盈亏
   ├─ 每个单元格可编辑，OCR 字段标黄待确认
   └─ 系统对比 DB.holdings 上次快照，标红异常变动（数量大幅变化等）
   ▼
[用户确认] 点击"确认落库"
   ├─ 逐项校验：数值合法性、标的名称在已知列表或新标的
   └─ confirmed=true → 写入 DB.holdings[date] + DB.overview[date]
   ▼
DB.snapshots[date] 留存（image_base64 / uploaded_at / ocr_status / confirmed）
```

#### 3.5.3 OCR 识别状态

| ocr_status | 含义 | 用户路径 |
|---|---|---|
| success | 全部字段识别成功 | 直接进入确认表格 |
| partial | 部分字段未识别 | 未识别字段标红，用户手填 |
| failed | 识别失败 | 弹窗提示，回退到 DAQ-2 手动录入 |
| skipped | 用户跳过截图，直接手动录入 | 不写入 snapshots，仅写 holdings |

#### 3.5.4 边界条件
- **截图 > 5MB**：上传前压缩，或拒绝并提示。
- **OCR 识别为新标的**：标记为"新标的"，用户可补全 instruments 主数据（v1.3 完整功能，v1.1 仅记录 name）。
- **同一日重复上传**：覆盖前次 snapshots，holdings 不变（除非用户再次确认）。
- **隐私边界**：方案 B 必须明确告知"截图将上传至第三方 OCR 服务"，默认关闭，用户主动开启。

#### 3.5.5 技术方案待决项（留给技术方案阶段）
1. OCR 方案 A vs B 的准确率与延迟实测对比
2. base64 存 localStorage vs IndexedDB 的容量与性能权衡
3. 截图压缩策略（分辨率/格式）
4. 新标的识别与 DB.instruments 的联动写入

#### 3.5.6 v1.2/v1.3 扩展点
- v1.3：OCR 可预填 industry 候选（基于标的名匹配 instruments）。
- v2.x：批量截图导入历史持仓。

#### 4.2.1 交易流水

```typescript
// 创建交易（R1/R2 共用）
createTrade(input: TradeInput): Trade

deleteTrade(id: string): void
```

#### 4.2.2 配对引擎（DAA-1）

```typescript
// 计算单笔买入的未平仓数量
calcQtyOpen(buyTradeId: string): number

// 获取对账视图数据（R3 用）
getReconciliationView(filter: {
  dateRange?: [Date, Date],
  names?: string[],
  sellTypes?: SellType[],
  closureStatus?: ClosureStatus[]

  - 返回：按标的分组的买卖配对树
```

#### 4.2.3 截图上传（DAQ-6）

```typescript
// 上传截图并 OCR
uploadSnapshot(date: string, imageBase64: string): {
  ocrStatus: 'success' | 'partial' | 'failed',
  prefill: HoldingsPrefill[]
}
  - 副作用：写入 DB.snapshots[date]（image_base64, ocr_status, ocr_raw）
  - 不写入 holdings/overview（待用户确认）

// 确认落库
confirmSnapshot(date: string, holdings: Holdings[], overview: Overview): void
  - 校验：数值合法性
  - 副作用：写入 DB.holdings[date], DB.overview[date]；更新 DB.snapshots[date].confirmed=true
```

#### 4.2.4 复盘（S1）


### 4.3 状态机：交易生命周期

```
                ┌─────────────┐
买入记录创建    │  UNLINKED    │  qty_open = amount
─────────────▶ │  （未关联卖出）│
                └──────┬──────┘
                       │ 卖出关联（兑现/证伪/失效）
                       ▼
                ┌─────────────┐
                │  PARTIAL     │  0 < qty_consumed < amount
                │  （部分平仓） │
                └──────┬──────┘
                       │ 累计消耗 = amount
                       ▼
                ┌─────────────┐
                │   CLOSED     │  qty_open = 0
                │  （已平仓）   │
                └─────────────┘

注：违规卖出不改变任何买入记录状态，但独立标记为"违规交易"。
```

### 5.4 关键交互铁律

1. **R1/R2 校验在保存按钮层强制**，不允许跳过；任一必填字段为空，保存按钮禁用。
2. **R2 自动带出未平仓买入**，用户无需手动查找；若列表为空，强制 sell_type 只能选"违规"。
3. **DAQ-6 OCR 仅预填**，所有字段在 confirmed=true 之前不写入业务数据。
4. **DAQ-6 失败回退**：OCR 失败时自动切换到 DAQ-2 手动录入，不阻塞流程。
5. **S1 自动保存**：复盘区任何输入实时写入 localStorage，防止丢失。
6. **R3 违规清单默认折叠**：仅当存在违规时自动展开，避免无违规时占用空间。

## 六、异常处理与边界条件汇总

| 场景 | 处理 |
|---|---|
| R1 必填字段为空 | 保存按钮禁用 + 字段红框 |
| R1 止损位 ≥ 价格 | 允许保存，弹窗警告 |
| R1 目标区间下沿 > 现价 | 允许保存，弹窗警告 |
| R2 未平仓买入不存在 | linked_buy_id 列表灰显，sell_type 强制"违规" |
| R2 关联数量超出未平仓 | 保存禁用 + 提示"超出可关联数量 X 股" |
| R2 违规 sell_note < 5 字 | 保存禁用 + 提示"违规说明至少 5 字" |
| DAQ-6 截图 > 5MB | 拒绝上传 + 提示压缩 |
| DAQ-6 OCR 失败 | 弹窗提示 + 自动切换 DAQ-2 手动录入 |
| DAQ-6 OCR 识别为新标的 | 标黄"新标的"，用户确认后落 holdings（instruments 主数据 v1.3 补全） |
| S1 当日无交易 | operations 段为空数组，仍可保存 |
| S1 当日无 holdings 快照 | pnl_attribution 段显示"请先录入当日持仓" |
| localStorage 容量超限 | 提示清理历史 snapshots（image_base64 占用大） |
| 同一日重复创建 trades | 允许（同一日多笔交易正常） |
| 跨日修改历史 trade | 允许（修正录入错误），但 R3 显示"已修改"标记 |

## 八、为技术方案预留的待决项

> 以下决策点不影响 PRD 边界，但技术方案阶段必须明确。

1. **OCR 方案选型**：浏览器端 Tesseract.js vs 云端 API（隐私权衡）
2. **截图存储介质**：localStorage base64 vs IndexedDB（容量权衡，5MB+ 截图建议 IndexedDB）
3. **配比策略**：用户手选 vs FIFO 默认（v1.1 默认手选，v1.2 可加开关）
4. **trade.id 生成**：UUID vs 时间戳递增（多设备同步预留，虽然 v1.x 不做云同步）
5. **OCR 置信度阈值**：低于某阈值自动标红还是统一手填（建议：低于 0.7 自动标红）
6. **数据迁移**：V1.0 现有 DB 数据如何平滑迁移到 v1.1（trades 表为空，holdings/overview 沿用）
7. **性能预算**：R3 对账页在 trades 数量 >500 时的响应时间（建议 <500ms，必要时加索引）
