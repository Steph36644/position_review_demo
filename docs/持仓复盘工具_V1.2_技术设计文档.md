## 二、技术栈选型

**沿用 v1.1.2 全部选型，零新增依赖。**

| 层次 | 选型 | 说明 |
|---|---|---|
| 前端框架 | 原生 JavaScript（ES6+，IIFE + `App` 命名空间） | 沿用 |
| UI 样式 | Tailwind CSS（CDN） | 沿用 |
| 图表 | Chart.js 4.x（CDN） | **复用**：水位环形仪表用 doughnut 类型实现，与 pieChart 同一实例管理 |
| 存储 | localStorage（结构化）+ IndexedDB（截图） | 沿用；新增 `pr2_plan` key |
| 构建/部署 | 无构建，纯静态 | 沿用 |

**关键决策**：

- **决策 1：水位仪表用 Chart.js doughnut 而非自绘 SVG/Canvas**。理由：Chart.js 已引入且稳定；色带弧长动态绘制可用 `rotation`/`circumference` 或三段背景色数据实现；自绘成本高且需维护动画。三段色带实现为"背景环（3 段静态弧）+ 当前值高亮弧（动态）"双层 doughnut。
- **决策 2：告警/水位/归因判定为纯函数服务，不引入状态管理库**。单日数据量 ≤15 持仓、1 个 overview，全量重算成本 <1ms，无需缓存与增量更新，每次数据变更后全量重算并触发渲染回调。
- **决策 3：归因默认值不落库，仅覆盖/保存时落库**。`pnl_attribution[name]` 存储的是"用户确认值"；展示层取值顺序 = 已存值 → DAA-4 默认计算值。避免 trades 变更后历史默认值脏数据。

### 3.3 渲染编排（重算触发链）

```
数据变更事件
  ├─ saveSnapshot(当日持仓/总览保存)      ─┐
  ├─ createTrade/updateTrade/deleteTrade ─┼─▶ App.AlertBannerController.recalc()
  ├─ PlanService.savePlan(plan 变更)      ─┤         │
  └─ 切换看板日期(dateSelect change)     ─┘         ▼
                              AlertService.evaluate(date) 全量重算
                                         │
              ┌──────────────────────────┼──────────────────────────┐
              ▼                          ▼                          ▼
   DashboardController           ReviewService              AlertBannerController
   .renderWaterLevel(水位卡片)   .syncWaterLevel(date)       .render(横幅)
   （持仓卡片归因由               （写回 position_in_band     （忽略名单过滤后渲染）
     AttributionService 渲染）    与 water_level）
```

- `recalc()` 为唯一重算入口，内部防抖 100ms，避免一次批量操作（如 OCR 确认多行）重复渲染。
- 复盘 Tab 不在前台时仅做数据写回，不操作复盘 DOM；切回复盘 Tab 时 `ReviewController.load` 读取最新值渲染。

### 4.4 计算口径（与 PRD §3.1.2 一致，全产品唯一实现于 AlertService）

```javascript
position_pct = overview.market_value / overview.total_assets * 100
single_pct(h) = h.market_value / overview.total_assets * 100   // 仅未清仓
cash_pct = (overview.total_assets - overview.market_value) / overview.total_assets * 100
```

- 分母恒为**总资产**；`total_assets` 为空或 ≤0 时全部指标返回 null，不判定。
- 市值字段直接读 v1.1.2 落库的 `h.market_value` / `overview.market_value`（已为计算落库值），不重复计算；读取时做 null 防御。

## 五、核心模块设计

### 5.1 PlanService（DAQ-3 / P1-1）

```typescript
initDefault(): Plan                  // 无 plan 时写入默认值并落库
getPlan(): Plan                      // 读取（必然存在，initDefault 兜底）
validatePlan(input): {valid, errors} // 范围 + lo<hi 校验
savePlan(input): Plan                // 校验→落库（updated_at）→ 触发 AlertBannerController.recalc({invalidateIgnores:true})
```

- 保存后通过事件参数 `invalidateIgnores:true` 使当日 `ignored_alerts` 失效（数据保留作留痕，渲染过滤时忽略之；实现：recalc 时将当日 review 的 `ignored_alerts` 整体移入 `ignored_alerts_history` 字段？——**简化决策**：不增设历史字段，直接将 `ignored_alerts` 清空并追加一条 `attribution_overrides` 无关联——**最终决策**：清空当日 `ignored_alerts` 即可，PRD 仅要求"留痕到复盘"指忽略发生时的记录，失效后复盘小节展示"已因计划变更失效"即可；实现上清空数组并在复盘小节渲染时若无记录则不显示。为保留失效痕迹，清空前把每条记录复制进新字段 `ignored_alerts_expired`。复盘"已忽略告警"小节合并展示两组，expired 组置灰标注"计划已调整，失效"。
- **阈值可设置（PRD §3.1.1 强约束）**：告警三项判定阈值（total_position_band / single_position_max / cash_min）全部来自 plan 用户设置值，AlertService 不内置任何固定阈值；代码默认值仅在首次初始化时写入 plan，之后一切判定以用户设置为准。设置弹窗命名为"仓位计划与告警阈值设置"，3 项判定阈值与 single_industry_max（v1.3 预留）全部可编辑，保存后触发 `AlertBannerController.recalc({invalidateIgnores:true})` 即时重算。

### 5.2 AlertService（DAA-2 + DAA-3，纯函数）

```typescript
/** 水位计算（DAA-2） */
calcWaterLevel(overview, plan): WaterLevel | null
// WaterLevel = {position_pct, band:[lo,hi], status:'in'|'above'|'below', dev_pp}
// 边界：pct 等于边界 → in（闭区间）；dev_pp = 越界时与最近边界的差（带符号1位小数），
//        带内时另算距上限/下限距离供展示

/** 三维度告警判定（DAA-3，维度注册表可插拔） */
evaluateAlerts(date): AlertItem[]
// AlertItem = {dim, name?, threshold, actual, dev_pp?, message, target:{type, anchor}}
//   dim='position' → target={type:'water'}
//   dim='single'   → target={type:'holding', anchor:name}
//   dim='cash'     → target={type:'water'}
// 判定数据：overview/holdings 取该 date；total_assets 缺失 → []
// 注册表：DIM_EVALUATORS = {position: fn, single: fn, cash: fn}
//         （v1.3 追加 industry/style 评估器即可）

/** 忽略过滤 */
filterIgnored(alerts, review): AlertItem[]
// 以 dim+name 为忽略键；review.ignored_alerts 中的项被过滤

/** 忽略（写留痕） */
ignoreAlert(date, alertItem): void
// 追加至 reviews[date].ignored_alerts（含 ignored_at），落库
```

- `dev_pp` 统一 `Math.round(x * 10) / 10`。
- `evaluateAlerts` 同时返回水位（供卡片与复盘写回），调用方一次取值。

### 5.4 AlertBannerController（P1-3）

**DOM**（`#alertBanner`，置于 `#tab-dashboard` 顶部、`overview` 区之上）：

```html
<div id="alertBanner" class="hidden">
  <div id="abHeader">⚠ N 项仓位告警  [收起/展开]</div>
  <ul id="abList">
    <li data-dim="single" data-name="科创50">
      <span class="ab-msg">科创50 占比 27.3%，超过单标的上限 25%</span>
      <button class="ab-goto">查看</button>
      <button class="ab-ignore">今日忽略</button>
    </li> …
  </ul>
</div>
```

**行为**：

- `recalc()`：调 `AlertService.evaluateAlerts(currentDate)` → `filterIgnored` → 非空渲染并自动展开，空则隐藏。
- **查看跳转**：
  - `target.type='holding'`：`document.querySelector` 定位持仓卡片（dashboard 卡片渲染时写 `data-holding-name` 属性），`scrollIntoView({behavior:'smooth', block:'center'})` + 添加 `flash-highlight` 类 1.6s（CSS keyframe 背景闪烁）。
  - `target.type='water'`：展开 `#wlBreakdown` 并滚动至水位卡片。
- **今日忽略**：`AlertService.ignoreAlert(date, item)` → 重渲染横幅 → 若复盘 Tab 已加载同一日期，同步刷新其忽略小节（经 `App.App` 提供轻量事件 `App.Events.emit('review:alertsChanged', date)`，复盘控制器订阅；单用户单页，直接函数调用亦可——**决策**：用直接调用 `App.ReviewController.refreshAlertsSection(date)`，避免引入事件系统）。
- 折叠态记忆：`sessionStorage` 记录当日是否手动收起（展开新告警出现则重置为展开）。

### 5.5 AttributionService（DAA-4 / S2）

```typescript
/** 单源读取：标的当日生效标签 */
getTag(date, name): {tag, source: 'override'|'default', locked: bool}
// 1) reviews[date].pnl_attribution[name] 存在且为合法枚举 → {tag, source:'override',
//    locked: tag 属违规锁定集合判定见下}
//    （历史自由文本值：原样返回，source:'override'，locked:false，可改选）
// 2) 否则 → {tag: computeDefault(date, name), source:'default'}

/** DAA-4 默认计算（优先级：违规>风控>兑现>持有>待归因） */
computeDefault(date, name): string
// 当日该标的 effective trades（复用 IndexManager.isEffectiveTrade）：
//   含 sell_type=违规     → 体系外-违规
//   含 证伪 或 失效       → 体系内-风控
//   含 兑现               → 体系内-兑现
//   无卖出且 getOpenBuys(name).length>0 → 体系内-持有
//   否则 → 待归因

/** 违规锁定判定（下拉可用选项集） */
isLockedToOut(date, name): bool
// 当日该标的含 sell_type=违规 的 effective trade → true
// 与当前标签无关：即使曾被覆盖，只要当日存在违规卖出即锁定（防洗白）

/** 用户覆盖（留痕） */
setTag(date, name, newTag): void
// 校验：isLockedToOut && newTag ∈ 体系内 → 抛 AttributionLockedException
// oldTag = getTag(date,name).tag
// reviews[date] 不存在则创建（createReview 默认值）
// pnl_attribution[name] = newTag
// 若 oldTag !== newTag → attribution_overrides 追加 {name, from: oldTag, to: newTag, at: now}
// 落库 saveReviews

/** 当日全部标的标签（复盘②段/看板渲染共用） */
getTagsForDate(date): Map<name, {tag, source, locked}>
// 标的集合 = 当日 holdings（含 cleared）∪ 当日卖出 trades 的 name
```

### 5.6 写回时机（position_in_band / water_level）

统一在 `AlertBannerController.recalc()` 内完成：评估出 WaterLevel 后调 `ReviewService.syncWaterLevel(date, wl)`：

```javascript
function syncWaterLevel(date, wl) {
  const review = db().reviews[date];
  if (!review) {
    if (!wl) return;              // 无复盘且无水位：不创建空记录
    db().reviews[date] = App.Models.createReview({position_in_band: wl.status==='in', water_level: wl});
  } else {
    review.position_in_band = wl ? (wl.status==='in') : null;
    review.water_level = wl;
  }
  App.LocalStorageRepo.saveReviews();
}
```

- **简化决策**：不复位 ignored_alerts/attribution 等字段，sync 只触碰 position_in_band/water_level 两字段。

## 七、状态机设计

### 7.1 告警生命周期

```
数据变更/plan 变更/切日期
        │
        ▼
  EVALUATED（全量重算）
        │
   有超阈项？
   ├─ 否 → HIDDEN（横幅不渲染）
   └─ 是 → SHOWN（自动展开）
              │
              ├─ 用户"今日忽略"单项 → IGNORED（写入 reviews.ignored_alerts，当日不再展示）
              │        │
              │        ├─ 跨自然日 → 失效（新日期重新 EVALUATED）
              │        └─ plan 变更 → 移入 ignored_alerts_expired → 重新 EVALUATED
              └─ 数值继续恶化 → 保持 IGNORED（v1.2 不重复弹出）
```

忽略键 = `dim + name`（如 `single:科创50`、`position:`、`cash:`）。

### 7.2 归因标签生命周期

```
快照/trades 变更
   │
   ▼
DEFAULT 计算（不落库）─── 看板/复盘展示 source='default'
   │
   ├─ 用户一键填入复盘 → 初值写入 pnl_attribution（source 转 'override' 语义上视为确认）
   └─ 用户下拉改选 → setTag：写入 pnl_attribution + attribution_overrides 留痕
        │
        └─ 违规锁定标的：选项集 = {体系外-违规, 体系外-判断失误}；改选体系内 → AttributionLockedException
```

## 八、关键技术点与难点

### 8.1 难点 1：环形仪表的"色带 + 当前值"表达

- 三段色带用单 dataset 弧长实现（[lo, hi−lo, 100−hi]），plan 变更仅改 data 后 `update()`。
- 当前值指示用 Chart.js 自定义 plugin `afterDraw(chart)`：按 `position_pct/100 * 360° − 90°` 计算角度，从 cutout 半径处向外画 3px 线段 + 端点小圆点；颜色取 status 色。
- pct > 100（杠杆情形）：钳制到 100 绘制，文案显示实际值。
- Chart 实例与 pieChart/barChart 同生命周期管理（dashboard renderAll 时 destroy 旧实例防泄漏——v1.1.2 已有 chart 管理逻辑，水位 chart 纳入同一管理器）。

### 8.2 难点 2：归因单源一致性

- 唯一写入口 `AttributionService.setTag`；看板与复盘的下拉均只调它；渲染均读 `getTag/getTagsForDate`。
- 双向同步用**直接函数调用**（看板改选 → `ReviewController.refreshAttribution`；复盘改选 → `DashboardController.renderAttributionTags`），调用前判断对方 Tab 是否已初始化对应日期，避免空 DOM 操作。
- trades 变更（如补录一笔违规卖出）后，`computeDefault` 结果变化但**不覆盖**已存 pnl_attribution；锁定状态（isLockedToOut）实时重算，渲染时若已存值违反当前锁定（历史遗留），UI 强制按锁定集合渲染并提示用户改选。

### 8.3 难点 3：忽略失效与留痕的平衡

- plan 变更 → 当日 `ignored_alerts` 数组逐项移入 `ignored_alerts_expired`（追加 `expired_reason: 'plan_changed'`），清空原数组，立即重算展示。
- 复盘小节同时渲染两组；导出备份天然包含全部留痕。

### 8.4 难点 4：collectReview 置空 position_in_band 的兼容修复

v1.1.2 [reviewController.js](../../v1.1/v1.1.2/js/controllers/reviewController.js) `collectReview()` 硬编码 `position_in_band: null`，自动保存会把 AlertService 写回的值抹掉。v1.2 修复：`collectReview` 不再返回 position_in_band/water_level 字段，autoSave 合并时保留 `existing.position_in_band / water_level / ignored_alerts / attribution_overrides`（与 operations/created_at 同策略）。**此修复必须在 M2 阶段最先落地**，否则水位写回被复盘自动保存覆盖。

## 九、异常处理与边界条件

| 场景 | 处理 | 位置 |
|---|---|---|
| total_assets 空/≤0 | calcWaterLevel 返回 null；水位显示「—」；告警不判定；复盘③段「—」 | AlertService |
| plan 缺失/损坏 | initDefault 以默认值重建并 warn | PlanService |
| plan 参数非法 | savePlan 抛 ValidationException；弹窗按钮禁用 | PlanService/Controller |
| pct 恰等于边界 | 判定 in（闭区间，含 cash_min：cash_pct == cash_min 不告警） | AlertService |
| pct > 100 或 < 0（数据异常） | 正常判定（>上限告警），图表钳制绘制 | AlertService/渲染 |
| 违规改体系内 | setTag 抛 AttributionLockedException；UI 下拉无该选项 | AttributionService |
| 历史自由文本归因值 | getTag 原样返回；下拉中作为额外选项保留显示 | AttributionService |
| 复盘自动保存覆盖水位 | collectReview 不返回水位字段（8.4 修复） | ReviewController |
| 重复忽略同一告警 | ignoreAlert 幂等（同 dim+name 已存在则跳过） | AlertService |
| localStorage 写满 | 沿用 StorageFullException 链路 | LocalStorageRepo |

## 十、数据迁移方案（v1.1.2 → v1.2）

- **plan**：首次启动 v1.2.0 时 `PlanService.initDefault()` 写入默认值（无版本标记需求，缺失即初始化）。
